# 第四部分：Agent 面试备战文章——《除了老套路，还能怎么准备？》

> 说明：该部分为备考文章中整理的六大方向题目，逐条整理作答。

## 76. 你做的 Agent 解决什么问题？为什么这个问题需要用 Agent 而不是普通规则？

【技术点】Agent 场景判断（必考认知题）

【答案】

**（结合 Aether 项目作答）**：Aether 解决"**多步骤、跨工具、依赖实时反馈与自主决策**的复杂任务自动化"——如旅游行程规划（需搜索实时信息、多约束平衡）、代码审查流水线（多 Agent 协作）、并行主题研究。

**为什么用 Agent 而不是规则**（判断标准：**路径决策权在谁手里**）：
- **规则（Workflow）**：流程预先编排死，适合**步骤确定、路径可枚举**的场景（如订单状态机流转）——确定性高、可测试、成本低；
- **Agent**：**路径无法预先枚举**、每一步依赖中间反馈（搜索结果的下一步取决于结果内容）、需要自主规划与工具调用——如"规划杭州 5 天避暑行程"：需要实时天气/交通信息、用户偏好澄清、多方案权衡，写死流程不可能覆盖；
- **工程立场（加分句）**："**能用 Workflow 解决的别上 Agent**"——自主性是用来对付"路径真的无法预先枚举"的场景的，不是拿来炫技的；Agent 有模型成本、延迟、不可控风险（幻觉、死循环）。

**常见误区**：为了简历好看强行上 Agent（无场景支撑，面试官一追就露馅）；答不出"决策权"这个判断标准；把"用了 LLM"当"用了 Agent"（LLM 只是工具，Agent 是自主循环）。

## 77. Agent 的架构是怎么设计的？画一下核心模块和数据流向。

【技术点】Agent 架构 / 数据流

【答案】

**（结合 Aether 项目作答）**

**核心模块**（对应 Aether 真实代码）：
1. **入口/触发层**（`AgentServiceController`）：HTTP/SSE 接收用户消息；
2. **会话管理层**（`ChatService` → `SessionRepository`）：会话创建/恢复/持久化；
3. **装配注册层**（`ArmoryService` → `AgentRegistry`）：YAML 配置 → Agent 实例；
4. **执行引擎**（`ReActAgent`/`PlanActAgent` + `ModelInvoker` + `ToolExecutor`）：ReAct 循环；
5. **工具系统**（`ToolRegistry` + MCP/技能书/Python）；**记忆系统**（`MemoryFacade` → `PgvectorVectorStore`）；
6. **上下文管理**（`ContextManager` + `TokenBudget`）；**编排**（`GraphExecutor` + `SubAgentOrchestrator`）；
7. **安全**（`PermissionEngine` + `JwtAuthFilter`）；**可观测**（`AgentEventPublisher` + 日志/metrics）。

**数据流向（核心链路）**：
```
用户消息 → Controller → ChatService.handleMessageStream
→ AgentRegistry 取 Agent → ReActAgent.execute
→ [循环] ModelInvoker(模型) ←→ ToolExecutor(工具)
        ↑ 上下文(ContextManager 注入记忆/历史)      ↓
        ↑                               工具结果回流(压缩/截断)
→ RuntimeEvent 流(textDelta/toolCall/toolResult/permissionAsking/done)
→ Controller 序列化为 SSE(data: {...}) → 前端展示
→ 持久化：SessionRepository(PG/Redis) + CheckpointCollector(每5轮)
```

**常见误区**：只画模块不画数据流（面试官要"数据流向"）；把执行引擎画成黑盒（要能讲 ReAct 循环细节）；漏掉安全/观测/持久化（生产要素）。

## 78. 工具调用是怎么实现的？如果工具返回了异常数据，你的 Agent 怎么处理？

【技术点】Function Calling / 工具异常处理

【答案】

**（结合 Aether 项目作答）**

**工具调用完整流程**：
1. **工具声明**：把工具（MCP/技能书/Python）注册进 `ToolRegistry`，工具描述 + 参数 JSON Schema 随**系统消息**发给模型（Aether 通过 `ToolExecutor` 管理）；
2. **模型决策**：模型判断需要工具时，返回结构化 `tool_calls`（工具名 + 参数）；
3. **参数校验**：`ToolValidation` 校验参数（类型/必填/范围）；
4. **执行**：`ToolExecutor` 调对应工具（MCP 走 `SSE/Stdio/Local` 服务、技能书走 `SkillsToolAdapter`、Python 走 `PythonServicePort`）；
5. **结果回流**：`ToolResult` 返回（成功 `toolError=false` 或失败 `toolError=true` + 结构化错误），**作为用户消息回填模型**继续推理；
6. **事件透出**：`toolCall`/`toolResult` 事件流式推给前端（可见性）。

**异常数据处理（重点）**：
1. **结构化错误而非堆栈**：工具异常不抛框架，转成 `{"status":"failed","error_type":"Timeout","error_message":"...","retry_after":5}`——模型能理解并决策（重试/换工具/告知用户）；
2. **格式不符**：工具返回非预期格式（Markdown 混入、JSON 损坏）→ 解析失败时给模型"解析失败"信号，让其重试或换方式调用；
3. **超时/重试**：MCP 请求超时可配（`request-timeout`），重试走 `ResilientChatModelExecutor` 的退避策略；
4. **内容安全**：工具输出含敏感信息 → `SensitiveArgMaskRule` 脱敏后再给模型；
5. **防注入**：工具返回内容可能含恶意指令（prompt injection）→ `InjectionGuardRule` 检测；
6. **结果截断**：超长结果截断/摘要（避免上下文爆窗——token 黑洞场景）；
7. **兜底**：连续失败触发熔断（循环检测），转人工。

**常见误区**：工具异常直接抛给框架（模型看到异常栈无法决策）；不校验工具返回格式（下游解析炸）；工具结果全量进上下文（token 爆炸）；不防注入（工具返回的恶意内容直接当指令执行）。

## 79. 工具调用失败怎么兜底？重试策略怎么设计的？多个工具同时触发时，优先级怎么定？

【技术点】工具重试 / 调度策略

【答案】

**失败兜底（分层）**：
1. **单次失败**：结构化错误返回模型 → 模型自主决策（重试/换工具/向用户说明）——**让模型参与兜底**是第一层；
2. **自动重试**：可重试错误（超时、429、5xx）指数退避重试（`RetryBackoff`），重试上限（如 3 次）；
3. **降级链**：同能力工具降级（搜索 A → 搜索 B）；模型 Provider fallback（OpenAI → Anthropic → DashScope）；
4. **熔断**：同一工具连续失败 N 次 → 临时熔断（不再调用，直接告知模型）；
5. **人工介入**：`permissionAsking` 挂起（PAUSED）交用户确认/提供替代输入；
6. **终态兜底**：任务仍失败 → 返回部分结果 + 明确失败原因（不让用户拿到静默失败）。

**重试策略设计要点**：① 错误分类先行（`DefaultModelErrorClassifier`：可重试 vs 不可重试——400/认证错误重试无意义）；② 退避算法（指数 + 抖动，防重试风暴）；③ 重试上限 + 超时总预算；④ **幂等性**（重试的工具必须幂等——写操作要幂等键，避免重复下单）；⑤ 重试计入成本（token/时间预算）。

**多工具优先级（决策因素）**：
1. **成本优先**：便宜工具优先（本地/缓存先查）；
2. **精度优先**：高精度工具优先（RAG 检索先精确后模糊）；
3. **依赖顺序**：有依赖的必须按序（先查用户身份再查订单）；
4. **并行度**：无依赖的并行执行（Aether `parallel` 工作流）；
5. **策略可配**：YAML 中工具列表顺序即默认优先级（`tool-mcp-list`），`ToolAllowlistRule` 可限制可用集。

**常见误区**：无差别重试（不可重试错误也重试，浪费 + 放大故障）；重试不幂等（重复副作用）；不设熔断（故障工具反复打）；优先级拍脑袋（要有成本/依赖/精度依据）。

## 80. MCP 协议了解吗？它解决了什么问题？和 Function Calling 什么关系？

【技术点】MCP 协议（腾讯高频，2025 必考）

【答案】

**核心概念**：MCP（Model Context Protocol，模型上下文协议，Anthropic 2024 年底开源）是 **Agent ↔ 工具**之间的**开放标准化协议**——类比"AI 界的 USB-C"：一次接入、处处可用。

**解决什么问题**：① **工具接入碎片化**——每个框架（LangChain/自定义）各写各的工具适配，MCP 统一了"工具发现（list_tools）、调用（call_tool）、资源（resources）、提示（prompts）、采样（sampling）"的标准接口；② **生态复用**——写一次 MCP Server（SSE/Stdio/HTTP 传输），任何支持 MCP 的客户端都能用；③ **解耦**——工具提供方不用关心消费方是哪个 Agent 框架；④ **安全**——能力边界清晰（权限、资源作用域）。

**与 Function Calling 的关系**：
- **Function Calling**：模型厂商（OpenAI 等）提供的"**模型输出结构化 tool_calls**"能力——是**模型侧**的机制（推理层）；
- **MCP**：**工具侧**的标准协议（工具如何被发现/调用/传输）——是**应用层**的机制；
- **关系**：两者互补——MCP 提供工具接入标准，Function Calling 负责让模型决定调用哪个工具；Spring AI 的 `ToolCallback`/`McpToolUtils` 把 MCP 工具适配为模型可用的 function 定义。

**Aether 项目实例**：Aether 通过 Spring AI MCP 集成，`SSEToolMcpCreateService`（远程 SSE）、`StdioToolMcpCreateService`（本地进程）、`LocalToolMcpCreateService` 三种接入方式；YAML 的 `tool-mcp-list` 声明（如 baidu-search 走 SSE 到百度 MCP 服务）；`McpRefreshController`（`/api/mcp/refresh`）支持运行时刷新工具。

**常见误区**：把 MCP 与 Function Calling 混为一谈（一个工具层一个模型层）；以为 MCP 只有 SSE（还有 Stdio/HTTP/Streamable HTTP）；忽略 MCP 的安全面（工具能力边界、凭据管理）；不区分 MCP 与 A2A（A2A 是 Agent 间协议）。

## 81. 短期记忆、长期记忆分别怎么实现？记忆的写入时机是什么？什么时候触发回忆？（小红书凉经 10 追问版）

【技术点】记忆系统实现（见第 59 题，补充写入/召回时机）

【答案】

**实现**（详见第 59 题）：短期 = `ContextManager` 会话上下文 + 压缩；长期 = `MemoryFacade`（`DefaultMemoryFacade`）+ `MemoryStore` + `PgvectorVectorStore` + 用户画像。

**写入时机（重点）**：
1. **会话关键节点**：用户显式表达偏好/身份/结论（"我喜欢吃辣"）→ 抽取写入（`SessionMemoryExtractor` 识别）；
2. **任务完成/总结时**：一轮对话结束或任务完成，把"结论、用户决定、未完成事项"摘要沉淀为长期记忆（`session-end` 抽取）；
3. **上下文压缩时**：`CompactionPipeline` 压缩前把高价值信息先落入长期记忆（防丢失）；
4. **主动触发**：用户要求记住（"记住这个"）/ 语义阈值（信息重要度打分——不是每句话都记，防噪音）；
5. 写入**异步化**：`remember` 返回 `CompletableFuture`（`EncodingFlow` 后台生成 embedding），不阻塞主流程。

**召回时机（重点）**：
1. **会话启动时**：注入用户画像（`ChatService.injectMemory` 处理 `{memory}` 占位符）；
2. **语义相关时**：用户问题与历史记忆语义相似度超过阈值 → `recall(query)`（Top-K，`max-results=10`）；
3. **任务延续**：跨会话续做任务时按任务上下文召回；
4. **预算控制**：召回结果按 `memory-char-limit`（2200 字符）截断注入，超预算丢弃低权重记忆；
5. 召回排序：**相关度权重 + 时间衰减**（`MemorySearchResult`）。

**常见误区**：所有对话都写入长期记忆（噪音污染检索）；无权重/衰减（旧记忆和新记忆同等权重）；写入阻塞主流程（应异步）；召回结果不做预算截断（挤占上下文）。

## 82. 上下文窗口满了，你的处理策略是什么？截断、摘要还是外部存储？

【技术点】上下文溢出处理（必考）

【答案】

**（结合 Aether 项目作答——三级策略，不是单选）**：

**① 预控（尽量别让它满）**：`TokenBudget` 实时监控（成本 + 窗口双维度），接近阈值预警；工具结果截断；记忆注入限预算（`memory-char-limit`）。

**② 压缩（满了之后的第一选择）**：
- **微压缩**：先丢低价值内容（闲聊、重复、已完成的中间推理）；
- **自动压缩**：`ContextManager` 触发 `AutoCompactResult`——把历史消息**摘要化**（要求保留：结论、数字、偏好、未完成事项）；
- **多步管道**：`CompactionPipeline` 分层处理（不同消息不同策略）；
- **透明**：`compactBoundary` 事件推前端，用户感知"上下文已压缩"。

**③ 外部存储（真正放不下时）**：
- **长期记忆落库**：关键信息进 `MemoryStore`（pgvector），需要时 `{memory}` 召回（见第 81 题）——上下文放不下的信息**移到外部存储**，这是"外部存储"的本质；
- **对话分页/分段**：历史消息存 `PgSessionRepository`，需要时按需加载（`session_messages` 接口）；
- **检查点恢复**：长任务分段（`checkpointInterval=5`），每段独立上下文，段间只传结论。

**取舍结论**：**截断最差**（丢信息无感知）；**摘要是主流**（但要做好结构化保留 + 记忆沉淀防丢失）；**外部存储是兜底**（适合超长会话与跨会话延续）。生产上三者组合：预算预控 → 压缩摘要 → 关键信息落外部存储。

**常见误区**：直接把窗口尾部截断（用户最早的偏好没了）；只压缩不沉淀（摘要本身也占 token，且关键信息可能丢——要配合记忆抽取）；不做预控（被动等爆）。

## 83. 如果记忆里存了错误信息，后续任务被污染了，你怎么发现和修正？

【技术点】记忆纠错（高级追问）

【答案】

**发现（怎么发现）**：
1. **用户反馈信号**：用户纠正（"我说的是上海不是南京"）→ 触发记忆更新/删除——**用户显式纠错是最可靠信号**；
2. **输出不一致检测**：Agent 回答与记忆矛盾（如用户说"我 5 年前入职"但记忆说"2 年经验"）→ Critic 校验模块检测冲突（`CurationPipeline`/`ResultRefiner` 可做一致性检查）；
3. **记忆质量评估**：定期用评测集验证记忆召回对任务成功率的影响，badcase 回流（错误记忆导致失败的任务）；
4. **过期检测**：时间衰减（旧记忆权重降低），超过有效期（TTL）不再注入；
5. **日志回溯**：结构化日志（`logs/aether-agent.json`）记录每次注入的记忆内容，问题任务可回溯"是哪条记忆带偏的"。

**修正（怎么修）**：
1. **覆盖而非追加**：新记忆与旧记忆相似度超高 → **合并/覆盖**（`MemoryStore` 去重逻辑），而不是追加一条矛盾的；
2. **显式删除**：`clear(scope)` / 按内容删除（用户说"忘掉这个"）；
3. **版本化**：记忆带时间戳与来源，冲突时以**最近一次用户确认**为准；
4. **置信度标记**：低置信度记忆（模型推断的）标注"推断"不强制注入；用户显式说的标记"确认"；
5. **人工纠错入口**：前端提供记忆管理界面（查看/删除/编辑）——Aether 前端（Vue3 工程）可扩展；
6. **预防**：写入时过滤（不是所有话都进长期记忆——`SessionMemoryExtractor` 筛选 + 重要性判断），源头减少错误记忆。

**常见误区**：错误记忆无发现机制（靠用户自己发现）；追加式写入导致矛盾记忆并存；不区分"用户确认"与"模型推断"（置信度）；没有删除/覆盖能力（记忆只能增不能改）。

## 84. 你的 Agent 如果一天有 10 万请求，架构能扛住吗？瓶颈在哪？

【技术点】Agent 系统容量设计（字节高频）

【答案】

**（结合 Aether 项目作答——先算账，再找瓶颈，再给方案）**

**算账（关键！量化思考）**：10 万请求/天 ≈ 每秒 ~1.2 QPS（均匀）≈ 高峰 10-30 QPS。但**每个请求背后是多次模型调用**（ReAct 循环 3-10 次）→ 模型 API 调用量 = 请求量 × 平均轮次 ≈ 30-300 QPS 级模型调用。瓶颈分析：
1. **模型 API 配额/限流**：最大瓶颈——模型 Provider 的 TPM（每分钟 token）限制；方案：多 Provider/多 key 轮换（`RotatingCredentialPool`）、请求排队、降级（`ResilientChatModelExecutor`）；
2. **应用线程池**：`ThreadPoolConfig` core=20/max=50/queue=5000——QPS 高峰超线程处理能力会排队（`CallerRunsPolicy` 背压）；方案：按需扩容、任务削峰（MQ 异步化）；
3. **数据库**：会话/记忆写入（`PgSessionRepository`、pgvector）——连接池 25；方案：读写分离、批量写、缓存（Caffeine）；
4. **Redis**：会话缓存/限流计数器——单点容量与网络；
5. **流式连接数**：SSE 长连接数（每个流式会话持连接）——WebFlux/Reactor Netty 事件驱动可扛，但需控制并发流（`SpawnGate`/限流）；
6. **上下文/内存**：并发 Agent 的上下文对象驻留内存 → 堆压力（G1 调优、检查点落盘释放）；
7. **成本**：10 万请求 × 平均 token × 单价——`TokenBudget` 熔断 + 模型选型（便宜模型分流）。

**方案（按优先级）**：① 先算清瓶颈（指标化：模型调用 QPS、队列深度、DB 连接、堆使用）；② 异步化（请求入队 + 回调/轮询结果，`AsyncDelegationService` 已有异步委派能力）；③ 水平扩容（无状态化——会话/检查点已持久化，可多实例）；④ 缓存（热点问答语义缓存）；⑤ 限流与降级（`RateLimitFilter` + 熔断）。

**常见误区**：不量化直接说"扛得住"（要算 QPS、算模型调用放大）；只看应用层不看模型配额（模型是最大瓶颈）；流式长连接数被忽略；不考虑成本（10 万请求的 token 账单）。

## 85. 怎么评估 Agent 的效果？你用哪些指标？（含：任务成功率怎么定义、怎么统计）

【技术点】Agent 评测（2025 年高频新方向）

【答案】

**指标分层（关键：区分"能力指标"与"工程指标"）**：
1. **任务成功率（核心）**：定义要**可操作**——"任务完成且结果满足验收标准"。统计：黄金用例集（Golden Set）端到端跑分——每个用例预置输入 + 期望输出（可用 LLM-as-judge 或人工标注判定）；统计口径 = 通过用例 / 总用例；线上可加"用户满意度/采纳率"（用户是否采纳 Agent 输出）；
2. **单点能力指标**：工具调用成功率（调用成功/总调用）、召回准确率（RAG）、格式合法率（JSON 解析成功）、错误处理率（失败后成功恢复）；
3. **效率与成本**：平均轮次（轮次越少越好）、平均延迟（P50/P99）、单任务 token 成本、成本/成功任务；
4. **稳定性**：同任务多次运行的**方差**（Agent 有随机性，方差大说明不可控）、超时率、死循环率；
5. **安全指标**：危险操作触发率、注入攻击拦截率、敏感信息泄露数；
6. **用户侧**：留存、NPS、badcase 反馈率。

**统计与闭环（工程化要点）**：① 评测集构建（真实用户问题采样 + 专家标注期望结果）；② **LLM-as-judge + 规则双判**（规则兜底防 judge 幻觉）；③ 线上日志回流 badcase（失败任务自动打标进评测集）；④ 回归门禁（新版本必须过评测集才能上线）；⑤ A/B 对比（新策略 vs 旧策略）。

**常见误区**：只说"效果不错"没有指标；任务成功率定义模糊（什么叫完成？要验收标准）；只测功能不测成本/方差；评测集不迭代（badcase 不回流——面试官强调"评测闭环"）。

## 86. 线上出问题了，你怎么排查？从监控到定位到修复的完整流程是什么？（含 trace 怎么做）

【技术点】可观测性 / 线上排查（字节高频）

【答案】

**（结合 Aether 项目作答）**

**① 监控层（先看到问题）**：
- **指标**：Prometheus（`actuator/prometheus` 暴露 health/info/metrics）+ Micrometer——JVM 内存/GC、线程池队列深度、请求 QPS/延迟、模型调用失败率、token 消耗；
- **日志**：结构化 JSON 日志（`logstash-logback-encoder` → `logs/aether-agent.json`），全链路 **MDC traceId**（`MdcFilter` 注入）——一次用户请求的所有日志带同一 traceId；
- **事件**：Agent 执行事件流（`AgentEventPublisher` → RuntimeEvent）可落 trace（`aether.graph.trace.persistence=true` 图级 trace 异步落盘）；
- **告警**：指标阈值告警（失败率、队列深度、错误日志关键词）。

**② 定位层（顺着 trace 找断点）**：按 traceId 串联整条链路（用户请求 → Controller → ChatService → ReAct 循环 → 模型调用/工具调用），看**哪一跳失败**（模型超时？工具返回异常？上下文爆窗？成本熔断？权限挂起？）——`textDelta/toolCall/toolResult/error` 事件时间线即 Agent 执行流水账；配合会话记录（`session_messages`）还原现场。

**③ 修复层**：定位后按根因修复（配置调整/代码修复/数据补偿），修复后跑回归（评测集），并**沉淀 badcase**。

**④ 复盘**：事故复盘（影响面、根因、改进项、监控补漏——"下次能否更早发现"）。

**常见误区**：日志不带 traceId（跨服务/跨调用无法串联）；只有错误日志没有执行轨迹（Agent 要记录每次模型调用/工具调用的事件流）；修完不补监控（下次同样问题靠人肉发现）；忽略结构化日志（非 JSON 无法被日志平台聚合查询）。

## 87. token 成本怎么算，怎么降？（Token 消耗增长过快如何定位优化）

【技术点】成本优化（字节高频，见第 64 题补充成本计算）

【答案】

**怎么算**：
- 单价：输入 token 单价 × 输入量 + 输出 token 单价 × 输出量（不同模型不同价）；
- 单任务成本 = Σ（每次模型调用：(system + 历史 + 工具定义 + 用户消息) 输入 token + 输出 token）× 单价；
- Aether 的 `ModelPricingRegistry` 维护模型单价，`TokenBudget` 累计成本并按 `maxCostUsd` 熔断。

**怎么降（按收益排序）**：
1. **上下文瘦身（最大头）**：历史压缩（`CompactionPipeline`）、工具结果截断、记忆注入限预算（`memory-char-limit`）、system prompt 精简、**prompt caching**（缓存 system/tools 定义，Anthropic `cache_control` 命中可省 90% 输入成本）；
2. **减少调用次数**：减少无谓轮次（循环检测、更准的工具选择）、缓存相似请求（语义缓存）；
3. **模型分层**：简单任务/重试用便宜模型（`inferProvider` 按 modelId 路由）、复杂任务用好模型——按任务难度路由；
4. **输出控制**：`max_tokens` 限制、要求精简输出、结构化输出防冗长；
5. **多 Agent 优化**：子 Agent 上下文隔离（不共享全部历史）、减少委派、合并小任务；
6. **重试治理**：错误分类准确、退避合理（重试是纯浪费）；
7. **预算与告警**：`TokenBudget` + 按会话/按用户成本告警（异常消耗早发现）。

**常见误区**：只看总账单不看分布（先按"会话/Agent/阶段"拆解）；只压输出不压输入（输入通常占大头）；忽略 prompt caching（大量重复计费）；重试不加治理（双倍成本）。

## 88. 幻觉怎么兜底？（补充题）

【技术点】幻觉治理（见第 62 题，此处给"兜底"完整版）

【答案】

**兜底四层**：
1. **输出校验层**：结构化输出（JSON Schema/function calling）强制格式；事实性校验（关键数字/实体与检索来源比对，不一致降级）；引用溯源（要求输出带来源）；
2. **评审层**：Critic/Reviewer Agent 二次审查（Aether 的 `CurationPipeline` 策展 + `ResultRefiner` 精修）；LLM-as-judge 对高风险回答做置信度评估；
3. **降级层**：低置信度 → 明确告知用户"这是 AI 生成，请核实"；高风险场景（医疗/金融）→ 拒绝回答或强制人工介入（`PermissionEngine` 审批）；
4. **提示层**：系统提示词内置红线（Aether 旅游 Agent："绝不虚构预订号码或声称能直接完成支付"）+ 引导模型区分"知识 vs 实时信息"（需要实时信息时**先检索再回答**，而不是编造）。

**常见误区**：只做提示层（幻觉是模型特性，提示只能减少）；校验层只验格式不验事实；高风险场景无人工闸门。

## 89. 你觉得 Agent 和 Workflow 的本质区别是什么？（开放题）

【技术点】认知题（必考，高分答法）

【答案】

**核心答案（一句话）**：**路径决策权在谁手里**——
- **Tool**：确定性函数，给参数出结果，零自主性；
- **Workflow**：人把流程编排死，LLM 只是流程中的节点，**走哪条路人说了算**（如订单状态机、审批流）；
- **Agent**：**把路径决策权交给模型**，下一步做什么运行时才知道（模型根据中间反馈自主选择工具/终止/换策略）。

**判断标准**：决策权在谁手里 + 路径能否预先枚举。
- 路径可枚举、步骤确定 → Workflow（确定性、可测试、低成本、可审计）；
- 路径不可预知、强依赖中间反馈 → Agent（自主规划、工具调用、动态调整）；
- **工程立场（加分）**：能用 Workflow 解决的别上 Agent；生产上常见**混合形态**：主流程 Workflow（显式 DAG/状态机，确定性）+ 关键节点 LLM 决策（Aether 的 `GraphExecutor` 编排 sequential/parallel 工作流，Agent 在节点内自主执行——正是"确定性框架 + 自主节点"的混合）。

**常见误区**：只答概念不答"判断标准"；把"用了 LLM"当 Agent（Workflow 也能用 LLM）；不知道混合形态（生产中很少纯 Agent 或纯 Workflow）。

## 90. 开源 Agent 框架（LangGraph/CrewAI/AutoGen）最大的缺陷是什么？（开放题）

【技术点】框架认知（阿里/字节高频）

【答案】

**（结合 Aether 项目——自研的动机就是回答这个问题）**

**共性缺陷**：
1. **黑盒循环与控制力不足**（LangChain 为代表）：Agent 循环藏在框架内部，**中断、恢复、人工介入、细粒度控制**难；状态管理不显式（LangGraph 已改进——显式 state + 图，但学习成本高）；
2. **Java 生态薄弱**：LangChain/LangGraph 是 Python 优先，Java 版（langchain4j 等）能力滞后、社区小——**Aether 选型 Java 自研的直接原因**（Java 17 + Spring Boot 3 生态，企业级后端天然契合）；
3. **生产级能力缺失**：多数开源框架是"研究/演示"导向——容错（错误分类/退避/降级）、成本控制（token 预算/熔断）、安全（权限审批/注入防护）、可观测（trace/审计）都要自己补（Aether 的 `ResilientChatModelExecutor`、`TokenBudget`、`PermissionEngine`、`MdcFilter` 就是补齐这些）；
4. **版本不稳定/升级破坏**：API 频繁变动（LangChain 0.x→1.x 破坏性变更），升级成本高；
5. **性能与依赖**：Python 框架 GIL/序列化开销，Java 框架依赖笨重（AutoGen 的 Docker 依赖等）；
6. **过度抽象**：为覆盖所有场景设计抽象层，简单场景反而绕（"配置地狱"）。

**答题技巧**：不要空泛批评——**选一个你真正用过的点**展开（如"LangChain 的 AgentExecutor 循环不可控，所以我自研了 `ReActAgent`，把终止条件、熔断、检查点都做成显式可配"），并承认开源的价值（生态、启发——Aether 借鉴了 AgentScope/CrewAI 的设计）。

**常见误区**：无脑吹或无脑黑；批评不落地（没有具体缺陷例子）；不提"借鉴了它什么"（显得没研究过）。

## 91. 大模型能力越来越强，Agent 工程师的价值在哪里？（开放题）

【技术点】职业认知题

【答案】

**价值核心：把"模型能力"转化为"可靠的业务能力"**——模型越强，工程化的杠杆越大：
1. **可靠性工程**：模型是概率性的，工程师负责让它稳定（容错、重试、降级、熔断、评测）——**把 90% 正确率提升到 99.9% 可用**靠的是工程；
2. **系统集成**：把模型接进真实业务（工具、数据、权限、审计、合规）——模型不懂业务，工程师懂；
3. **成本与效率**：模型调用有成本，工程师做上下文管理、缓存、模型分层——**同样的模型，工程好的团队成本差 10 倍**；
4. **安全与治理**：幻觉、注入、数据泄露、合规——工程师是最后防线；
5. **评测与迭代**：构建评测闭环，让模型/策略迭代有据可依；
6. **场景判断**：知道什么该用 Agent、什么不该用（决策权判断）——模型再强，用错场景也白搭。

**加分观点**：模型能力上升会"消灭"只会调 API 的初级岗位，但**工程化能力随模型能力提升而更稀缺**——Agent 工程师的价值是"让模型在真实世界安全高效地干活"。

**常见误区**：说"价值是调 prompt"（太浅）；说"价值是懂模型"（那是算法岗）；没讲出工程化这个差异化点。

## 94. 项目中的 Agent 主要应用在哪些场景？为什么选择使用 Agent 方案，而不是传统流程实现？

【技术点】场景判断（见第 76 题，补充场景清单）

【答案】

**Aether 已配置的 Agent 场景**（来自 `agent/*.yml`）：
1. **旅游规划 Agent**（Agent01）：搜索实时信息 + 多约束平衡 + 迭代修改——需要实时数据（RAG/搜索）与动态规划，规则写死不可行；
2. **代码审查流水线**（test-agent.yml）：CodeWriter → CodeReviewer → CodeRefactorer 多 Agent 协作——任务分解 + 跨 Agent 传参，确定性流程可编排但节点内需模型判断；

## 95. 在 Agent 开发过程中，使用了哪些技术框架？整体代码架构是如何设计的？（小红书凉经 5）

【技术点】技术栈 / 架构（见第 58 题，补框架清单）

【答案】

**技术框架**：Java 17 + Spring Boot 3.4.3 + **Spring AI**（ChatModel 抽象 + MCP 集成）、**RxJava 3**（`Flowable<RuntimeEvent>` 事件流）、PostgreSQL 16 + **pgvector**（向量记忆）、Redis/Caffeine（会话/缓存）、Spring Security 6 + JJWT（认证）、OpenTelemetry/Micrometer/Prometheus（可观测）、**LangChain4j/Google ADK**（依赖管理参考）、xfg-wrench-starter-design-framework（策略树装配）。

**整体代码架构（DDD 六边形 + 模块化单体）**：六模块分层（详见第 1 题）——`aether-trigger`（HTTP）→ `aether-api`（接口/DTO）→ `aether-domain`（领域核心：Agent 引擎/模型 SPI/记忆/工具/编排）→ `aether-infrastructure`（适配器：PG/Redis/MCP/凭据/检查点）→ `aether-types`（基础类型）→ `aether-app`（装配/启动）。

**架构设计要点（为什么这样设计）**：
1. **依赖倒置（Ports & Adapters）**：domain 定义接口（`SessionRepository`、`VectorStore`、`ModelProvider`），infrastructure 实现——可替换（PG ↔ Redis、不同模型 Provider）；
2. **模块化单体**：六模块内聚 + 依赖单向（domain 不依赖 trigger/infrastructure 实现），可拆微服务时边界清晰；
3. **配置即装配**：YAML 声明 Agent（模型/工具/工作流），运行时装配——新增 Agent 零代码；
4. **事件驱动流式**：RxJava Flowable 贯穿执行链路（背压 + 流式输出）。

**常见误区**：架构图与实现脱节（要能指着代码说）；只答框架名不答"为什么这么设计"；没有分层依赖规则（单向依赖是 DDD 的命门）。

## 96. OpenManus 采用了什么框架实现？你对它的整体设计有什么理解？（小红书凉经 6/14）

【技术点】OpenManus / 开源 Agent 框架认知

【答案】

**OpenManus 简介**：2025 年 3 月开源的**通用 AI 智能体**（MetaGPT 团队），设计目标是替代 Manus 的"全流程自主 Agent"——通过**多 Agent 协作**（Planner 规划 → Supervisor 监督 → ToolCaller 工具调用）完成从规划到执行的任务闭环。技术栈：Python + LLM API（Claude/GPT 等）+ 工具（浏览器、代码执行、文件操作）。

**整体设计理解（重点讲"设计思想"而非 API）**：
1. **多 Agent 分工**：Planner（任务分解/规划）、Supervisor（监控执行/纠偏）、ToolCaller（具体工具执行）——体现"**规划-执行分离**"思想（对应 Aether 的 Planner/Executor 角色与 `PlanActAgent`）；
2. **工具即能力**：核心是**工具调用闭环**（搜索、代码、文件）——Agent 的能力边界由工具集决定（Aether 同样以 `ToolRegistry` + MCP 扩展工具）；
3. **简单 vs Manus**：OpenManus 把 Manus 的黑盒流程**开源为可读的 Agent 循环**（透明、可控、可二次开发）——这正是开源框架的价值：**把"演示级能力"变成"可工程化的代码"**；
4. **局限（可补充）**：Python 单体、生产级能力（容错/成本/安全/可观测）仍需自建——呼应"开源框架缺生产能力"的认知（第 90 题）。

**答题技巧**：没实际用过就诚实说"了解其设计"；把 OpenManus 的设计与自己的项目对比（如"它用 Python + 多 Agent 分工，我的 Aether 用 Java + 自研 ReAct 引擎 + 编排"），展示判断力。

**常见误区**：把 OpenManus 当"Manus 的开源版"一句话带过（要讲设计结构）；不对比自身项目（体现不出深度）。

【技术点】Harness 认知（见第 67 题）

## 98. 多 Agent 协同执行时可能会遇到哪些性能瓶颈？比如资源竞争、调用效率等问题如何解决？（小红书凉经 8/16）

【技术点】多 Agent 性能（阿里/小红书高频）

【答案】

**瓶颈清单**：
1. **模型 API 配额与并发**：N 个 Agent 并发调模型 → 触发 Provider 限流（TPM 上限）——方案：请求排队/限流（`RateLimitFilter`）、多 key 轮换（`RotatingCredentialPool`）、降级（fallback 链）、`SpawnGate` 控制并发 spawn；
2. **线程/资源竞争**：并发 Agent 争用线程池（`ThreadPoolConfig` core=20/max=50）与数据库连接池（25）——方案：任务隔离（独立池）、有界队列 + 背压（`CallerRunsPolicy`）、异步化（`AsyncDelegationService`）；
3. **上下文内存膨胀**：每个并发 Agent 都持有完整上下文对象 → 堆压力——方案：检查点落盘（释放内存）、限制并发流数、上下文压缩；
4. **工具调用竞争**：多个 Agent 同时调同一外部服务 → 下游被打爆——方案：限流、超时、结果缓存（Caffeine/Redis）；
5. **结果聚合瓶颈**：`ChildResultAggregator` 串行聚合大量结果——方案：流式聚合、并行处理；
6. **状态一致性**：并发写会话/记忆 → 锁与幂等——方案：租约（`LeaseManager`）、幂等键、PG 事务；
7. **成本爆炸**：并发 × 多轮次 token——方案：`TokenBudget` 熔断 + 预算分摊（`DelegationBudget`）。

**解决思路框架**：先量化（并发数、模型调用 QPS、队列深度）→ 分层治理（入口限流 → 执行异步 → 资源隔离 → 成本熔断）→ 监控验证（指标 + trace）。

**常见误区**：只说"加机器"（瓶颈常在模型配额与资源竞争，不是机器）；忽略下游工具承受能力（并发放大打到外部服务）；无预算管控（并发 Agent 成本失控）。

## 99. 在实际应用中，如何控制 Agent 并发数量？有哪些限流或调度策略？（小红书凉经 9/17）

【技术点】Agent 并发控制

【答案】

**（结合 Aether 项目作答）**：
1. **入口限流**：`RateLimitFilter` 按用户/IP/QPS 限流（拒绝或排队）——第一道闸；
2. **信号量/并发配额**：`SpawnGate`（控制子 Agent spawn 数量）+ 全局并发数上限（信号量控制同时执行的 Agent 数）；
3. **线程池边界**：核心线程数/队列深度即并发上限（`ThreadPoolConfig` queue=5000 + `CallerRunsPolicy` 背压）；
4. **模型侧限流**：模型 Provider 配额感知——超 TPM 时排队/降级（`ResilientChatModelExecutor` + `RotatingCredentialPool`）；
5. **预算控制**：`TokenBudget`（`maxCostUsd` 熔断）+ `DelegationBudget`（子 Agent 预算分摊）；
6. **优先级调度**：重要用户/任务优先（队列分级）；长任务与短任务分流；
7. **异步化削峰**：高并发时请求入队（`AsyncDelegationService` 异步委派 + 持久化），结果异步回调/轮询；
8. **熔断降级**：系统过载时拒绝新任务（保护存量），向用户返回"稍后重试"。

**常见误区**：只限流不排队（直接拒绝对体验差——要分级降级）；无全局并发上限（各入口单独限流但总量失控）；忽略模型侧配额（应用层限了模型还是炸）。

## 100. ReAct 框架的核心思想是什么？具体执行流程是怎样的？（小红书凉经 11/19）

【技术点】ReAct（必考）

【答案】

**核心思想**：**Reasoning + Acting（推理 + 行动）交替循环**——模型在"思考（Thought）→ 行动（Action，调用工具）→ 观察（Observation，工具结果）"之间循环，**每步看到结果再决定下一步**，解决纯推理（CoT）无事实依据、纯行动无规划的问题。本质：**把决策过程与外部世界反馈闭环**。

**具体流程（对应 Aether 的 `ReActAgent.execute`）**：
```
Thought: 分析当前状态，决定下一步（"用户要查天气，我需要搜索"）
Action: 输出工具调用（tool_call：baidu-search，参数 query="杭州天气"）
Observation: 工具返回结果（"toolResult"）
→ 回到 Thought，循环直到：
   - 模型认为信息足够，输出最终答案（Final Answer）
   - 或达到终止条件（MAX_TURNS=100、取消、熔断、成本上限）
```
Aether 实现细节：`ReActAgent` 循环（`state.getCurrentTurn() < MAX_TURNS`），每轮：模型返回 → 有 `tool_calls` 则 `ToolExecutor` 执行并回填结果（`TurnMessage`）→ 无工具调用则输出最终文本；事件流（`textDelta`/`toolCall`/`toolResult`）实时推送；`ModelInvoker` 负责模型调用（含容错）。

**常见误区**：把 ReAct 当"背定义"（要能画出完整循环）；忽略终止条件（ReAct 没终止条件会死循环——`MAX_TURNS` + 熔断 + 取消令牌）；把 CoT 当 ReAct（CoT 无行动无工具）。

## 101. 在 Agent 架构中，Planner、Executor、Critic 分别承担什么职责？三者之间如何协同？（小红书凉经 12/20）Critic 模块具体解决什么问题？为什么需要 Critic，而不是直接采用 ReAct 流程？（小红书凉经 13/21）

【技术点】规划-执行-评审架构

【答案】

**职责**：
- **Planner（规划器）**：接收任务，**分解为子任务/步骤**（任务拆解、依赖分析、资源分配）——对应 Aether 的 `PlanActAgent` 与 `GraphExecutor` 的编排能力（`{outputKey}` 跨步骤传参）；
- **Executor（执行器）**：按计划**逐步骤执行**（调工具、调模型、产出结果）——对应 `ReActAgent`/`ToolExecutor`；
- **Critic（评审器/批评者）**：**检查执行结果**（质量、正确性、是否满足需求、是否遗漏），发现问题**反馈给 Executor 重新执行/修正**——对应 Aether 的 `CurationPipeline`（策展管道）与 `ResultRefiner`（结果精修），`test-agent.yml` 的 `CodeReviewerAgent` 本质上就是 Critic 角色。

**协同方式（循环）**：Planner 出计划 → Executor 执行 → Critic 评审 → 通过则交付 / 不通过则反馈（具体修改意见）给 Executor 迭代 → 迭代有上限（防死循环）→ 通过后聚合交付。

**为什么需要 Critic 而不是纯 ReAct（13/21 重点）**：
- **ReAct 的局限**：ReAct 是"**边想边做**"，每一步基于当前反馈决策，但**缺少"回头看"的校验环节**——它追求"做出来"，不保证"做对"；模型一步错可能一路错（缺乏外部检查点）；
- **Critic 的价值**：① **独立校验**：用不同的视角/标准检查结果（防模型"自我感觉良好"——self-consistency 之外的第三方视角）；② **质量把关**：错误早发现早修正（成本低于交付后返工）；③ **迭代闭环**：形成"执行-评审-修正"的正向循环，显著提升复杂任务成功率；
- **取舍**：Critic 增加一次模型调用成本——只在高价值/复杂任务启用，简单任务直接 ReAct（避免过度设计）。

**常见误区**：把 Critic 当"再来一遍"（要有明确评审标准/检查清单）；无迭代上限（Critic 与 Executor 死循环——要设 max 迭代）；纯 ReAct 无评审（错误一路带到结果）。

## 103. Redis 有哪些常见数据结构？不同数据结构底层实现原理分别是什么？（小红书凉经 15/25/26）

【技术点】Redis 数据结构（必考）

【答案】

**五大基础结构 + 底层实现**：
1. **String（字符串）**：底层 **SDS（简单动态字符串）**——`len/free/buf` 结构，O(1) 长度、二进制安全、预分配防频繁扩容；可存整数时用 int 编码（`set 100`），也可存 embstr/raw；
2. **List（列表）**：早期 `quicklist`（压缩列表 ziplist 分段 + 双向链表）；7.0 起 **listpack**；quicklist = 多个 listpack 节点组成的双向链表——兼顾内存紧凑与快速两端操作；
3. **Hash（哈希）**：元素少时 **listpack**（紧凑连续内存）；元素多时 **hashtable**（字典，渐进式 rehash 平滑扩容）；
4. **Set（集合）**：全整数且少时 **intset**（有序整数数组，二分查找）；否则 **hashtable**（value 为 null）；
5. **ZSet（有序集合）**：**skiplist（跳表）+ 字典**双结构——跳表按 score 排序（O(log n) 范围查询），字典按 member 找 score（O(1)）；元素少时用 **listpack**。

**进阶结构**：Bitmap（String 的位视图，见第 33 题）、HyperLogLog（基数统计，误差 ~0.81%，12KB 上限）、GEO（ZSet + 经纬度编码）、Stream（消息队列，5.0 新增）。

**Aether 项目实例**：Redis 存会话（`RedisSessionRepository`）、限流计数、缓存；Caffeine 本地缓存配合。

**常见误区**：把"编码转换"漏掉（小数据用紧凑编码，大数据用高级结构——面试常问"什么时候切换"）；说 List 是纯链表（quicklist/listpack 更准确）；跳表与红黑树对比不清楚（ZSet 用跳表而非红黑树：实现简单、范围查询天然有序、内存友好）。

## 105. 场景题：如果希望通过 Agent 实现广告投放策略的自动优化，让系统能够分析投放效果、自主判断最佳方案并执行迭代，你会如何设计整体方案？（小红书凉经 17/28，阿里系场景题）

【技术点】场景设计题（Agent + 业务闭环）

【答案】

**方案设计（按"数据 → 分析 → 决策 → 执行 → 反馈 → 安全"闭环）**：

**① 数据层（Agent 的"感知"）**：接入投放数据（展示/点击/转化/成本/ROI，按渠道/人群/创意维度）；定时任务/事件驱动拉取（SQL/BI 接口/CSV）；数据质量校验（缺失、异常值标记）。

**② 分析层（Agent 的"判断"）**：多 Agent 分工——**分析师 Agent**（趋势分析、归因：哪些变量影响 ROI）、**策略 Agent**（基于分析产出候选策略：调预算/改出价/换创意定向）、**评审 Agent（Critic）**（评估策略合理性，拒绝无依据建议——防幻觉决策）。

**③ 决策与执行层**：策略变更分类——**低风险（预算调整）自动执行**（有阈值边界）；**高风险（创意修改、大额预算）走审批**（`PermissionEngine` 挂起 → 人工确认）；执行走投放平台 API（工具调用，幂等 + 限流）。

**④ 反馈闭环（关键）**：执行后**监控效果指标** → 与预期对比 → 成功则沉淀策略（进记忆/规则库）；失败则回滚 + 记录 badcase → 迭代。**A/B 实验**：新策略小流量验证再全量。

**⑤ 安全与治理**：预算硬上限（成本熔断——`TokenBudget` 思想）、操作审计（`@Auditable`）、可回滚、人工闸门、权限分级。

**设计要点（评分点）**：① **闭环**（分析-决策-执行-反馈-迭代缺一不可）；② **风险分级**（不是全自动，低风险自动 + 高风险审批）；③ **实验思维**（小流量验证）；④ **防失控**（预算上限、回滚、审计）；⑤ **量化评估**（ROI 提升目标 + 指标监控）。

**常见误区**：设计成"全自动无审批"（大厂要的是安全可控）；没有反馈与迭代闭环（一次性优化不是"自动迭代"）；无预算/成本硬约束（投放场景成本失控是事故）；不区分策略风险等级。
